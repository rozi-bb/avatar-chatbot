# AGENTS.md

Instructions for AI coding assistants working in this repository.

## Project

Wayan, a voice chatbot for the lobby kiosk of Taman Gumitir, a fictional heritage hotel in Bali. A portfolio demo: a LangGraph agent (Python 3.13) gives the Wayan avatar its words. The avatar itself (Rive rig, Azure TTS, lip sync) lives in a separate repo.

## Commands

```bash
uv run langgraph dev                  # dev server + Studio (http://127.0.0.1:2024)
uv run pytest -q                      # unit tests, no API calls
uv run pytest -q -m integration       # integration tests, real API calls
uv run ruff check .                   # lint
uv run ruff format .                  # format
uv run mypy --strict src evals        # type check
uv run python -m evals.run            # LangSmith evaluations (real API calls)
```

## Layout

- `langgraph.json`: tells the dev server where the graph is (`./src/agent/graph.py:graph`)
- `src/agent/graph.py`: the model setup, state, context, nodes, and the graph (`build_graph`)
- `src/agent/prompts.py`: Wayan's system prompt
- `src/agent/reply.py`: the reply contract (`check_reply`) and the fixed lines it uses
- `evals/`: LangSmith datasets and code evaluators (`format.py`) and the runner (`run.py`)
- `tests/unit_tests/`, `tests/integration_tests/`
- `knowledge/`, `docs/`: see the table above

Follow the structure generated by the LangGraph template; don't reorganize it. Split `graph.py` into modules (`state.py`, `nodes.py`, ...) only when a feature needs it.

## Rules

- Always use type hints; code must pass `mypy --strict`.
- Every new node gets a unit test.
- Tests that call a real API are marked `@pytest.mark.integration`.
- Assert on the STRUCTURE of a response, not on exact strings.
- Don't use LangChain or LangGraph APIs whose names start with `_` (internal).
- Check LangChain and LangGraph APIs against the official docs (the `docs-langchain` and `reference-langchain` MCP servers) before using them. This project uses the v1 APIs.
- Don't add a dependency or change `langgraph.json` without saying so first.
- NEVER write an API key value in any file. Keys live only in `.env`, which is git-ignored; never print or log them. Keep `.env.example` in sync with the variable names, with empty values.
- Google-style docstrings on public functions. No comments that restate the code; comment only non-obvious reasons.

## Product rules live in code

A prompt can be talked out of a rule; code can't. The rules in `docs/prd.md` §10 that matter most are enforced in code:

- The reply contract (allowed tags, at most 400 characters, no markdown or emoji) is checked by code after the model, not only asked for in the prompt.
- Emergency and staff requests get fixed replies, never model-written ones.
- Hotel facts come only from `knowledge/hotel.md`. Never hard-code hotel facts in prompts or code.
- Evaluations pass a fixed "now" through the runtime context, so results are reproducible.

## Workflow

- Work on ONE unchecked task from `docs/roadmap.md` per session.
- Before coding a new feature: EXPLAIN the plan first, then wait until I say I understand.
- When done: tick the task, run the tests, report the results as they are, then STOP AND WAIT FOR ME.
